# 실험: 손글씨 "사진" 입력 시 전처리 문제

- **날짜**: 2026-08-28
- **동기**: 과제 1을 그림판 파일이 아니라 **종이에 써서 카메라로 찍은 사진**으로 해보고 싶었음 (`Downloads\20260828_1723*.jpg` 4장 = 3, 8, 7, 4)
- **결과**: 가이드 기본 전처리로는 4장 중 1장만 맞음. 원인을 찾아 전처리를 고치니 3장 맞음.

## 1. 증상

`task1_predict_digit.py` 로 사진 4장을 예측한 결과:

| 사진 | 실제 숫자 | 가이드 전처리 예측 | 확률 |
|---|---|---|---|
| 20260828_172345 | 3 | **0** ❌ | 0:67.5% / 2:10.2% / 8:8.2% |
| 20260828_172353 | 8 | 8 ✅ | 8:69.9% / 0:11.0% / 2:8.3% |
| 20260828_172357 | 7 | **0** ❌ | 0:48.7% / 2:15.9% / 8:14.5% |
| 20260828_172400 | 4 | **8** ❌ | 8:52.9% / 0:21.3% / 4:9.2% |

그림판으로 만든 `my_digit.png`(숫자 2)는 잘 맞았는데(2, 85.96%) 사진만 유독 틀림.

## 2. 원인 — 전처리가 "깨끗한 디지털 이미지"를 가정함

`task1_predict_digit.py` 전처리(28~37번 줄)는 이렇게 동작한다:

1. 흑백 변환
2. 평균 밝기 > 127 이면 색 반전 (흰 배경 → 검은 배경, MNIST 방향)
3. **`image.point(lambda v: 255 if v > 20 else 0).getbbox()`** 로 숫자 영역만 잘라냄
4. 잘라낸 숫자를 20×20으로 축소 → 28×28 캔버스 정중앙 배치
5. `/255` 정규화

문제는 **3번**이다. 임계값 `20`은 "배경이 거의 완전한 검정(0~20)"이라고 가정한다.
그림판 이미지는 배경이 정확히 흰색(255)→반전 후 0 이라 잘 맞는다.

하지만 **카메라 사진**은 조명·그림자 때문에 배경이 완전한 흰색이 아니라 회색이다.
직접 측정한 값:

| 사진 | 원본 평균 | 반전 후 배경 밝기 | 가이드 bbox (임계값 20) |
|---|---|---|---|
| 172345 | 137.9 | ~117 | **(0, 0, 1632, 1568) = 이미지 전체** |
| 172353 | 142.4 | ~113 | **전체** |
| 172357 | 146.0 | ~109 | **전체** |
| 172400 | 148.6 | ~106 | **전체** |

반전 후 배경이 ~110 이라 `> 20` 조건을 전부 통과 → 배경까지 "숫자"로 판단 →
**bbox가 이미지 전체 = 크롭이 아무 일도 안 함.**

그 결과 4번에서 "사진 전체(숫자 + 거대한 여백)"를 20×20으로 축소 →
숫자는 한가운데 자잘한 얼룩이 되고, 주변은 회색 사각형 → 모델은 사실상
"흐릿한 회색 네모"를 보게 되어 0·8 같은 뭉툭한 숫자로 찍는다.

(→ `photo_preprocessing_compare.png` 왼쪽 열: 회색 박스 안 작은 숫자)

## 3. 해결 — Otsu 자동 임계값으로 이진화

고정 임계값 `20` 대신 **Otsu 방법**으로 각 이미지마다 전경/배경을 가장 잘 가르는
임계값을 자동 계산해서 이진화한 뒤 크롭한다. (`photo_preprocessing_test.py`)

- Otsu = 히스토그램을 두 덩어리(배경/전경)로 나눴을 때 두 덩어리 사이 분산이
  최대가 되는 임계값을 찾는 고전 알고리즘. 조명이 달라도 이미지마다 알아서 맞춤.
- 추가로 마스크를 씌워 배경 회색 픽셀을 0으로 눌러줌(사진 잡음 제거).

계산된 Otsu 임계값: 사진마다 158~166 (고정값 20과 완전히 다름 → 왜 실패했는지 명확)

| 사진 | 실제 | 가이드 전처리 | **개선 전처리(Otsu)** |
|---|---|---|---|
| 172345 | 3 | 0 ❌ | 5 (56.9%), 2위 **3** (32.5%) — 여전히 틀림 |
| 172353 | 8 | 8 ✅ | **8** (99.0%) ✅ 확신 대폭 상승 |
| 172357 | 7 | 0 ❌ | **7** (64.8%) ✅ |
| 172400 | 4 | 8 ❌ | **4** (85.9%) ✅ |

1/4 → 3/4 로 개선.

## 4. 남은 실패 (172345, 숫자 3)

개선 전처리로도 3은 5로 오인식(3은 2위, 32.5%).

- 사진 속 3이 획이 매우 벌어지고 위쪽이 과도하게 넓게 그려짐 → 28×28로 줄이면
  위 곡선이 5의 각진 어깨처럼 보임 (`compare.png` 오른쪽 첫 줄)
- 가이드 4.4 지침과 정확히 일치하는 상황: **숫자를 너무 크게·가장자리에 닿게
  그리지 말 것. 중앙에 적당한 크기로.**
- MNIST 학습 데이터는 "적당히 반듯하게 쓴 미국식 숫자"라, 개성 강한 필체·기울기·
  벌어진 획에는 약하다 (모델 자체의 일반화 한계).

## 5. 배운 것 (심화 포인트)

1. **전처리는 입력 도메인 가정을 품고 있다.** 이 스크립트는 "그림판/스캔 = 깨끗한
   이진 이미지"를 가정했고, 사진이라는 다른 도메인에서 조용히 무너졌다(에러도 안 남).
2. **고정 임계값 vs 적응 임계값.** 조명이 변하는 실제 사진에는 Otsu/adaptive
   threshold가 필요. OpenCV `cv2.threshold(..., THRESH_OTSU)`, `adaptiveThreshold`.
3. **"모델이 틀렸다"와 "전처리가 틀렸다"를 구분해야 한다.** 여기서는 대부분
   전처리 문제였고(1→3개 개선), 3번만 진짜 모델 한계.
4. 더 가고 싶으면: 촬영 사진 augmentation(회전·기울기·명암)으로 재학습, 또는
   MNIST 대신 자기 필체 데이터 수집.
